# Usage-Carved Memory

> This document explains the **principles** behind v1 of this package's storage and
> retrieval system. The intended reader is a developer who uses the package or wants
> to understand its internals. It is a design explainer, not a code reference, and
> covers only what is implemented.
>
> Every concrete number in this document (thresholds, weights, and so on) is an
> **illustrative example**. Actual values are injected by the application as tuning
> parameters; defaults are defined in `src/tuning.ts`.
>
> The system assumes no particular kind of service. Whether it backs a conversational
> assistant or the session memory of a coding agent, it applies identically anywhere
> "facts about an entity accumulate and get retrieved again." Read "conversation"
> throughout as interaction logs in general — messages, session transcripts, etc.
>
> If terms like embedding, cosine similarity, kNN, or exponential decay are
> unfamiliar, consider reading the concepts appendix first:
> [usage-carved-memory-concepts.en.md](./usage-carved-memory-concepts.en.md)

---

## 1. Background — why score-based retrieval

External memory for an LLM sits between two forces.

- **Memory gains value as it accumulates.** The moment you delete a node, you lose
  the asset of "a memory we have carried for a long time." This system therefore
  assumes nodes are never deleted.
- **Memory gets harder to handle as it accumulates.** As the total size N grows, any
  approach of the form "read everything and reorganize" (full rebuilds, global
  clustering, batch decay over all rows) explodes with cost proportional to N.

The principle that resolves this tension is the system's name: **we do not compute
the "correct" graph. Usage carves it.**

- No LLM call ever sees the whole graph. LLM cost is proportional to the **delta
  ΔN**, not to the total N.
- Candidates are generated by vectors and SQL; only confirmation goes to an LLM.
  Every LLM call has O(1) context.
- Edges are not answers but **hypotheses**. Lay them down cheaply; usage reinforces
  them, disuse lets them sink.
- Judgments are soft (ranking), hence reversible. Wrong judgments must be cheap so
  that cheap models and cheap rules can be used — a design that absorbs error.
- **Forgetting is not deletion but a term in the retrieval ranking.** No batch job
  ever touches all rows.

Under these principles, retrieval naturally becomes not "return everything above a
threshold" but **"select the top N most worth recalling right now."** That selection
criterion is the score.

Threshold-cut retrieval has two structural failure modes. If no relevant memory
clears the threshold, nothing comes back (starvation); if many near-duplicates
crowd around the threshold, noise pours in (flooding). Score ranking with top-N
selection has neither — you always get "the best N available right now."

## 2. Data model

### Nodes (memories)

The unit of memory: a fact in natural language, one sentence to one paragraph.

| Field | Meaning |
|---|---|
| `content` | The memory text |
| `embedding` | Vector of the content. Regenerated when content is updated |
| `strength` | Stored strength [0, 1]. Rises with re-mention |
| `strength_updated_at` | When strength last changed — **the decay clock** |
| `retrieval_count`, `last_retrieved_at` | Usage record, written on every retrieval |

### Edges

A relation hypothesis between two memories. The natural key is `(from, to, type)`;
edges are stored directed but read undirected at retrieval time.

| Field | Meaning |
|---|---|
| `origin` | Who created it — `conversation` (context-confirmed) or `knn_seed` (embedding hypothesis) |
| `strength` | Stored strength [0, 1]. Born at its confidence level, raised by usage |
| `strength_updated_at` | The decay clock. Reset on every reinforcement |

One important thing about `origin`: **the consuming side (ranking, reinforcement,
decay) never looks at it.** Origin is not a type that changes behavior; it is the
signature of an automated writer. Any automated process (the gate, a migration)
must sign its output so that, if it turns out to be wrong, its output can be
revoked wholesale.

Conceptually the difference between the two origins is not "who found the
candidate" but **"did it pass contextual confirmation":**

- `conversation` — a link confirmed by an LLM that read the interaction and decided
  "these two memories are actually related." Born at a fixed, confirmed-grade
  strength.
- `knn_seed` — an unconfirmed hypothesis laid purely from embedding similarity.
  Born with the similarity as its strength; usage validates it afterwards.

### Strength and effective strength

Stored strength is the write-time value. What ranking actually reads is the
**effective strength**:

```
effective = stored × e^(−λ × days_since_last_reinforcement)
```

With λ (the decay constant) at 0, forgetting is off. With λ > 0, anything that goes
unreinforced sinks with time. This computation is a **read-time formula** — no
batch job that grinds down stored values exists, nor needs to. This is the
implementation of "forgetting = a ranking term."

> **A note for observers**: querying the DB directly shows you stored strength. In
> a long-running entity, frequently used edges pile up near the ceiling (1.0) and
> can look "all the same" — but the value the system actually consumes is the
> effective strength, which is spread continuously by usage cadence. Visualize,
> analyze, and debug using effective strength (`effectiveStrength()` or the formula
> above), not the stored value. The stored value plus the clock are the raw record
> — "confidence at last reinforcement, and when" — and the effective value is
> derivable from them at any moment.

## 3. Writing — the dedup gate (at insertion)

When the application throws an interaction at the package, the package's extraction
LLM pulls out facts worth storing. Right before being stored, each candidate passes
the **gate**: one vector lookup fetches the top-K nearest existing memories (the
embedding computed here is reused for storage), and the nearest similarity decides
the candidate's fate by band:

```
                similarity
  1.0 ┬─────────────────────────
      │  skip band: "this memory already exists"
      │  → do not create. Instead bump the existing node's strength
      │    (re-mention = reinforcement signal)
 skip ┼─────────────────────────
      │  gray zone: "unclear whether it's the same"
      │  → create it, link it strongly to the nearest neighbor, and record the
      │    pair in the merge-review ledger (judgment deferred)
 link ┼─────────────────────────
      │  seeding band: "a new fact, with plausible neighbors"
      │  → create it and lay knn_seed edges to top-K neighbors above the
      │    seeding floor (strength = similarity)
 floor┼─────────────────────────
      │  unconnected: create only
  0.0 ┴─────────────────────────
```

The logic of each band:

- **Skip band** — the reappearance of a near-identical sentence is a signal, not a
  bug. The same fact being mentioned again means that memory matters, so instead of
  creating a duplicate node, the existing node is reinforced. Nothing is lost — by
  definition, the skipped content already exists in a node.
- **Gray zone** — embeddings are polarity-blind. "Loves coffee" and "can no longer
  drink coffee" look similar on the surface and score high similarity while meaning
  the opposite. Skipping in this band would be dangerous, so the candidate is
  created, tied strongly to its nearest neighbor, and the pair is written to a
  ledger (sleep_jobs) that says "read the contents later and adjudicate."
  Not judging now is the judgment.
- **Seeding band** — a new fact with related candidates nearby. Whether those links
  are truly meaningful, nobody knows — so they are laid down cheaply as
  hypotheses. Correct hypotheses will be reinforced by usage; wrong ones will go
  unused and sink. Laying them costs nearly nothing (the gate's top-K result is
  reused; no extra query).

### How context edges form

Separately from seeding, the extraction LLM may point at memories — within "the
list of existing memories retrieved this turn" — that are actually related to a new
fact. Links formed this way are `conversation` edges. Folded down:

1. At retrieval time, the **embedding** chose the candidates (the working set), and
2. the extraction LLM, inside the interaction's **context**, confirmed which of
   them are truly related.

So even context edges got their candidates from the embedding. The only difference
from `knn_seed` is the confirmation step. The extraction LLM cannot link to
memories outside the retrieval boundary — seeding covers that blind spot, and
usage validates what seeding lays down.

### Conflict policy — strength only goes up

When inserts collide on the same `(from, to, type)`: **strength is updated only
upward, and the origin of the first writer is preserved.** For example, if a
context edge exists and a higher-similarity seed insert lands on the same pair,
only the strength rises; the origin stays `conversation`. Embedding signals may
reinforce a context edge but can never weaken or relabel it — the hierarchy of
write authority is enforced structurally.

The authority to remove or weaken an edge belongs to context alone (the extraction
LLM's link-removal judgment).

## 4. Reading — score-ranked retrieval

### The candidate pool: seeds + 1-hop expansion

When a query (the recent context of the current interaction) arrives:

1. **Vector seeds** — the top-k nodes by query embedding. Always k of them; no
   threshold cut.
2. **1-hop expansion** — for each seed, its edge-connected neighbors join the
   candidate pool. Direction is ignored (undirected read).

Candidates = seeds ∪ neighbors of seeds. The system never looks at the whole
graph — only one hop out from where the current query shines its light.

### The score — a weighted sum of four "reasons to recall"

Each candidate receives:

```
score = α·similarity + β·edge_activation + γ·recency + δ·node_strength

  similarity      = cos(query, node)                 … "directly relevant right now"
  edge_activation = max(eff. edge strength × that seed's similarity)
                                                     … "connected to what just came to mind"
  recency         = e^(−days_since_creation / scale) … "a recently formed memory"
  node_strength   = the node's effective strength    … "a repeatedly confirmed memory"
```

Why each term exists:

- **α (similarity)** — the search axis. With only this, the system is a search
  engine.
- **β (edge activation)** — the association axis. The more strongly a seed pulls,
  and the more relevant that seed itself is to the query, the more its neighbors
  surface. Note it is a **product** of effective edge strength and seed
  similarity — a strong edge with an irrelevant seed pulls nothing, and a relevant
  seed with a feeble edge pulls nothing. If a neighbor connects to several seeds,
  only the strongest pathway (max) counts.
- **γ (recency)** — the topicality axis. A memory created moments ago is likely
  relevant to the ongoing exchange. Based on **creation time**.
- **δ (node strength)** — the validation axis. A memory re-mentioned many times is
  likely core to the entity. The only term that operates independently of the
  query.

Note that γ and the decay in β·δ run on different clocks. γ asks "how long since
birth" (fixed scale); decay asks "how long since last reinforcement" (the λ dial).
Favoring newborn memories is γ's job; sinking fading ones is λ's.

### Selection and side effects

The top N by descending score are returned to the application — the working memory
the system "recalls" for this turn. Properties of the score:

- **It is never stored.** It is recomputed at every retrieval against that moment's
  query and clock. This is why decay works without batches.
- **Its absolute value is meaningless.** Only relative order is used, and since
  there is no threshold cut, there is no "nothing came to mind" failure mode.

Right after selection, two usage signals are recorded asynchronously (never
blocking the retrieval response):

- `retrieval_count` / `last_retrieved_at` updates on the selected nodes
- **strength bumps on the contributing edges** — edges that actually served as
  β-term pathways get slightly stronger, and their decay clocks reset

These side effects change the next retrieval's scores. **Today's selection shapes
tomorrow's selection** — a self-reinforcing loop, counterbalanced by λ pulling the
other way.

## 5. Carving — reinforcement and decay

Reinforcement signals are split across two axes:

| Signal | Target | When | Meaning |
|---|---|---|---|
| Re-mention bump | **node** | when the gate rules "skip" | "this fact was mentioned again" |
| Usage bump | **edge** | when it contributes to a ranked retrieval | "this connection proved useful" |

Node strength is the confirmed weight of the memory itself; edge strength is the
validated usefulness of a relation — separate, persistent states. Being retrieved
does not raise a node's strength (only its usage record). What strengthens a
memory is re-mention; what strengthens a connection is use.

Decay operates through the single λ, applied evenhandedly to nodes and edges. As a
result:

- **What keeps being used** — bumps keep resetting the clock, so effective strength
  holds. Even at the stored ceiling (1.0), the clock reset remains effective. Among
  ceiling-bound items the stored value no longer discriminates, but with λ on,
  **usage cadence takes over the discrimination** — a 1.0 used daily and a 1.0
  untouched for a month have very different effective strengths. In the long run
  the axis of discrimination migrates from "stored magnitude" to "recency of use,"
  and that is this design's intended end state.
- **What goes unused** — sinks exponentially with no write at all. It disappears
  from ranking, not from storage.
- **Revival** — if a sunken edge one day contributes to a retrieval again, the bump
  resets its clock and it returns instantly at its stored strength. Because the
  stored value was never ground down, revival is cheap — the cost of a wrong
  sinking is low. This is the error-absorbing design.

What survives is, in the end, defined by **bump inflow outpacing decay**. λ is the
dial that sets that equilibrium.

## 6. Variable glossary — roles, and what raising or lowering means

The values themselves are injected by the application. Here we only describe which
property of the system each dial moves.

### Gate (writing — what becomes memory)

| Variable | Role | Raise it | Lower it |
|---|---|---|---|
| Skip threshold | The "already exists" line | Fewer skips, more duplicates. Safe but messier graph | More skips. Too low and restatements carrying real information deltas get absorbed — memory loss |
| Gray-zone floor | The "ambiguous" line | Narrower gray zone; less deferral, most candidates just get created | Wider gray zone; more review-ledger entries and strong links. Trades against review throughput |
| Seeding similarity floor | Minimum similarity to lay a hypothesis | Sparser, cleaner graph; weaker associative pull | Weak hypotheses get laid too. β reaches further but noise and row count grow |
| Max seeds per creation | Cap on hypotheses per node | Denser graph — and more weeds for review/decay to handle | Only confident neighbors get connected |

The three lines must always satisfy `skip threshold > gray-zone floor > seeding
floor`; the package validator falls back to defaults on violation.

### Ranking (reading — what gets recalled)

| Variable | Raise it | Lower it |
|---|---|---|
| α (similarity) | Query-focused — closer to a search engine | Low-similarity nodes surface via connections and strength — association-driven |
| β (edge activation) | Seed neighbors come along strongly — "recall one, get the bundle." Too high and one seed's neighborhood dominates the list | The graph is ignored — everything invested in edges becomes meaningless |
| γ (recency) | Newborn memories favored — sensitive to the latest topics. Too high and old core facts get crowded out | Creation time is irrelevant — yesterday equals last year |
| δ (node strength) | Frequently re-mentioned memories favored in every query — the "what defines this entity" effect. Too high and popular nodes become the answer to everything | Re-mention history stops affecting retrieval |
| λ (decay constant) | Unused memories and links sink faster; the graph self-cleans quicker. Too high and even established facts sink without re-mention | At 0, forgetting is off — strength once earned is permanent |

One safety property of λ: it acts only on β and δ and **never touches α or γ**.
However far decay progresses, an old memory directly relevant to the query still
surfaces by similarity. What λ kills is the *association pathway*, not the
*search pathway*.

### Package-internal constants (not exposed to tuning)

Birth strengths are ordered: **context-confirmed > gray-zone link > seeding
floor**. This is an ordering of minimum guarantees, not a cap — a seed born from a
high similarity may exceed the confirmed grade. Bump sizes also come in two kinds:
the re-mention bump (nodes) is larger than the usage bump (edges), because one
explicit re-mention is a stronger signal than one implicit use.

## 7. Scenarios

All numbers are illustrative.

### 7.1 Insertion — the fate of three sentences

Existing memories: M1 "the user likes americanos," M2 "the user likes working from
cafés."

- Candidate A, "the user likes iced americanos" — similarity 0.98 to M1 (skip
  band). **Not created.** M1's node strength rises; the interaction re-confirmed a
  known preference.
- Candidate B, "the user can no longer drink coffee" — 0.91 to M1 (gray zone).
  Similar surface, possibly opposite polarity. **Created**, tied strongly to M1,
  and (B, M1, 0.91) is written to the merge-review ledger. The truth of the pair
  (contradiction? update? coexistence?) is decided later by an adjudicator that
  reads the contents.
- Candidate C, "the user took up hiking" — nearest is M2 at 0.72 (seeding band).
  **Created**, with a knn_seed edge to M2 (strength 0.72). Nobody has judged
  whether hiking and cafés are really related — it is a hypothesis.

### 7.2 Retrieval — why café talk tags along with "how's the hiking going?"

From the state above, the user asks "how's the hiking going?" (assume α=1, β=0.3.)

1. Vector seeding catches C (hiking; query similarity 0.85).
2. 1-hop expansion follows C's edges and adds M2 (cafés) to the candidates.
3. M2's score: its α term is low (query "hiking" vs cafés ≈ 0.3). But its β term =
   effective edge strength 0.72 × seed similarity 0.85 ≈ 0.61, times weight 0.3,
   adds 0.18. In the combined ranking, M2 overtakes nodes that are "unrelated to
   hiking but middling in surface similarity."
4. If M2 makes the top N, whatever generates the response talks about hiking while
   also holding the context "a user who likes working from cafés." And at that
   moment the C–M2 edge takes a bump — the hypothesis has been validated once.

Repeat this, and C–M2 hardens past the confirmed grade. Conversely, if the link
never proves useful, then with λ on it quietly sinks out of the β term. Either
way, **nobody ever explicitly judged this edge's truth** — usage carved it.

### 7.3 Four reasons a neighbor does not come along

A neighboring node fails to surface for one of four reasons:

1. **No edge** — without a connection to a seed, β = 0. It doesn't even enter the
   candidate pool (unless it becomes a seed by its own similarity).
2. **The edge has sunk** — long unused, its effective strength is near zero; the
   connection exists but pulls nothing.
3. **The seed is weak** — β is a product. Even a 1.0 edge attached to a seed only
   0.2-relevant to the query yields pull on the order of 0.2. A "strong
   connection" is not enough; it must be a strong connection *to something
   relevant right now*.
4. **It came along but lost the selection** — it entered the pool, but its total
   score fell below the top N. More relevant, stronger memories took the seats.

### 7.4 The life of an edge

```
[birth]    Born as a hypothesis (strength = similarity; low confidence)
   │
   ├─ used ──→ bumps accumulate ──→ passes confirmed grade ──→ saturates at 1.0
   │                                        │ still used: clock keeps resetting; effective stays 1.0
   │                                        │ unused: only effective strength sinks (stored stays 1.0)
   │                                        └ used again: clock resets → instant revival to effective 1.0
   │
   └─ unused ──→ (λ>0) effective strength sinks ──→ β contribution vanishes
                 = natural death in the ranking. The row remains. Nothing is deleted.
```

No write in the system lowers stored strength. All "weakening" happens in the
read-time effective value, which is why every sinking is reversible.

## 8. The application integration contract

The contract is one sentence: **the application does not judge; it throws. Memory
judges.**

What the application supplies:

- **Raw interaction logs** — conversation messages or agent session logs, passed
  as-is without choosing what to store. Extraction, dedup, linking, and
  reinforcement are all performed by the package.
- **entityId** — the isolation unit of memory. Every lookup and judgment happens
  within one entity.
- **An LLM adapter and an embedding service** — the package owns no models.
- **Tuning values** — the dials of chapter 6. Injected per request, so changes
  take effect immediately. Omitted fields use package defaults; invalid values are
  reverted to defaults by the validator.

What the application receives:

- **The working set** — the top N memories at retrieval time, meant to be injected
  into the response prompt as "what is currently remembered." The application
  never needs to report which memories were actually used in the response — usage
  signals were already recorded at retrieval granularity by the package.

The typical request flow:

```
Before generating:  getContext(recent interaction) ──→ working set of N ──→ inject into prompt
                                        └ (side effects) usage records, contributing-edge bumps

After generating:   afterResponse(recent interaction)
                        ──→ package builds its own working set via retrieval
                        ──→ extraction LLM extracts facts + points at related memories
                        ──→ gate pass → store / reinforce / seed / defer
```

In both steps the application's only job is to hand over the interaction. Whether
to store, how to handle duplicates, how connections form and fade — all of it is
carried out by the mechanisms this document described.

## 9. Boundary — what lies outside this document

- **The merge-review worker** — the consumer of the ledger (sleep_jobs) that the
  gray zone fills. Enqueueing is implemented today; adjudication (merge / update /
  coexist / unrelated) is a follow-up component.
- **Decay on by default** — λ defaults to 0 (off). Choosing its value is an
  operational decision grounded in production data (usage-interval distribution,
  reinforcement inflow, saturation rate).

Both items are extensions that follow this document's principles (ΔN-proportional
cost, soft judgments, usage carves) — they introduce no new principle.
